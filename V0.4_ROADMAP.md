# V0.4 Roadmap (alpha)

Priority-ordered plan for v0.4-alpha release. Merges V0.3 functional roadmap +
V0.3 performance roadmap into one execution plan. Each item ships as a
perf-tagged commit on the `ai/dev` branch.

---

## Phase 1 — Performance unblockers (shipped)

### 1.1 Per-request log suppression
**Tagged:** `v0.3.0-beta1`
- `src/main.zig`: routing log → `log.debug`
- `lib/zigora_proxy/root.zig`: request completion log → `log.debug`
- `lib/zigora_core/service.zig`: listening log → `log.debug`
- Expected gain: +80-120% debug throughput

### 1.2 Response body streaming
**Tagged:** `v0.4.0-alpha1`
- Removed 8K `resp_buf` stack allocation per request
- Parse response headers first, write immediately to client
- Stream body chunks directly (Content-Length, chunked, or EOF)
- Responses > 8KB no longer truncated

### 1.3 Pre-allocated buffer pool
**Tagged:** `v0.4.0-alpha2`
- New `lib/zigora_core/buffer_pool.zig`: 16-slot atomic-cursor ring
- `PerRequestBuffers { read: [4096], write: [4096], header: [8192] }`
- Service borrows from pool per-request; proxy uses pooled buffers instead of stack
- ~20K less stack allocation per request

### 1.4 Multi-listener parallel accept
**Tagged:** committed
- `Service.startService` spawns N accept futures when built listeners > 1
- Single listener path unchanged (inline accept loop)
- Accept loop extracted as private `acceptLoop` method

## Phase 2 — Functional features (alpha)

### 2.0 Signal handling (SIGTERM/SIGINT)
- **Tagged:** committed
- Server installs `std.posix.sigaction` for SIGTERM + SIGINT
- Global pointer to `Server` for handler callback → calls `shutdown()`
- `runForever` installs handlers before spawning service futures

### 2.1 Request body streaming (POST/PUT)
- **Tagged:** committed
- `BodyHint` struct describes transfer mode (none / content_length / chunked)
- `request.headers` detection for Content-Length
- `proxyToH1` forwards body bytes from client stream to upstream
- Content-Length mode streams directly; chunked mode noted as ponytail skip

### 2.2 Keepalive + ConnectionPool (deferred)
- **Status:** disabled for stability
- `process_new` returns `null` always (reverted from keepalive loop)
- ConnectionPool get/put wired into `proxyToH1` but connection reuse is not active
- **Re-enable when:** downstream conn reuse is tested in multi-threaded benchmarks

## Phase 3 — Pending (v0.4-beta)

### 3.1 Downstream keepalive (admit)
- Re-enable `process_new` → `?Stream` for HTTP/1.1 w/o `Connection: close`
- `handleConn` accept loop reuses returned stream
- Verified: multi-request-per-connection with `tc`

### 3.2 Keepalive upstream (PoolNode hot):
- Replace single mutex poolNode with lock-free ArrayQueue (Pingora-style 16-slot hot queue)
- Add idle connection eviction (timeout-based)
- Move pool.Lru to thread-local (per-service) instead of global

### 3.3 Backend health checks (TCP)
- `TcpHealthLoader.check(backend) → Result` — dial with timeout
- Background health check loop (idependently of accept)
- Unhealthy backends removed from active selection set

### 3.4 Structured request logging
- Use that `logging` callback to produce one line per request-finale
- This is: method, path, status, duration, bytes, upstream addr

### 3.5 All-fixture benchmark suite
- `benches/proxy_end_to_end.zig`: 1000 parallel connections, count 200s
- `zig build bench-proxy` step in build.zig
- Corp to baseline: 200 req/s goal (debug), 800+ (release)
