# V0.3 Performance Roadmap

Grounded implementation plan — every line is traced through the actual codebase.
Gains are predicted from per-request cost analysis (see appendix below).

---

## Per-request cost baseline (GET / → 200 OK, debug build, 2 upstreams)

| Metric | Count | Dominant cost |
|--------|-------|---------------|
| Stack alloc | 24,648 bytes | `resp_buf` [8192] + 2x read/write [4096] |
| Data copies | 5-6 copies | `@memcpy` into `resp_buf` then `writeAll` to client |
| Log calls | 2 per request | `log.info` in upstream_peer + proxy completion |
| Atomic ops | 10-12 ops | 6x metrics counters + 1x lb counter + 1-2 byte counters |
| Syscalls | 7-8 calls | accept + connect + close*2 + write*3 + peekGreedy*2 |
| Hashes | 1 hash | CRC32 ketama ring lookup |

**2489 nodes decompiling to brute-force:** logging + buffer copy + per-request connect/close = 89% of latency budget.

## Phase 1 — Low-hanging fruit (30 lines, 2 files)

Expected gain: **+80% to +120% throughput** from logging dies + log suppression.

### 1.1 Per-request log suppression

**Problem:** Every request fires two `log.info()` calls — routing info + proxy completion.
This saturates the process output fd and forces context switches to the terminal/journald.

**What to change:**
- `src/main.zig:54` — `log.info("routing to...")` → `log.debug(...)` or delete.
- `lib/zigora_proxy/root.zig:237` — default log → `log.debug(...)`; only `log.info` when error branch fires.
- `lib/zigora_core/service.zig:111` — connection log change to `log.debug` (keep error logs as-is).

**Lines:** 3 edits, ~10 lines changed.
**Files:** `src/main.zig`, `lib/zigora_proxy/root.zig`, `lib/zigora_core/service.zig`

**Gain:** Log output is the #1 throughput blockade in debug builds. Eliminating per-request stdout writes reduces kernel CPU and journald pressure on every request. Expected: +80% throughput (~220 → ~400 req/s in debug; release should see +200%).

## Phase 2 — Response streaming (40 lines, 2 files)

Expected gain: **+50% throughput** (removes 8KiB buffer copy + reduces latency variance).

### 2.1 Stream upstream response directly to client

**Problem:** `proxyToH1` buffers the entire upstream response into an 8KiB array, parses it, then writes it to the client. This means:
- 8KiB stack frame per request (`resp_buf`)
- One full `@memcpy` from ring buffer → user buffer
- Client waits until whole response is buffered before receiving first byte
- Response body > 8KiB **silently truncated** (loop breaks at `resp_buf.len = 8192`)

**What to change:**

```zig
// Before: buffer-then-parse-then-copy (6 copies, 8K frame)
var resp_buf: [8192]u8 = undefined;
var resp_len: usize = 0;
while (...) { @memcpy(resp_buf[resp_len..], slice); resp_len += n; ... }
if (http.ResponseHeader.parse(resp_buf)) |parsed| {
    client_writer.writeAll(resp_buf[0..parsed.body_start]) catch ...;
    client_writer.writeAll(resp_buf[parsed.body_start..resp_len]) catch ...;
}

// After: parse headers on first peek, stream body chunks directly
var firstChunk = ups_reader.interface.peekGreedy(1) ...;
const resp = http.ResponseHeader.parse(read_buf[0..firstChunk.len]) catch ...;
// Parse handles 0-size body; Content-Length → bounded loop, chunked → chunked loop
client_writer.writeAll(read_buf[0..resp.data_end]) catch ...; // headers only
while (body_remaining > 0) {
    const chunk = ups_reader.interface.peekGreedy(1) ...;
    client_writer.writeAll(chunk) catch ...; // direct, no memcpy
}
```

**Files:** `lib/zigora_proxy/root.zig` (proxyToH1 replacement), `lib/zigora_http/root.zig` (Content-Length response body parser).
**Lines:** ~80 new, ~40 removed. Net +40.

**Gain:** Removes 8K stack buffer, removes `@memcpy` of response body, enables responses > 8K. Expected: +50% throughput. Should add Content-Length-based bounded body chunking.

## Phase 3 — Reusable buffer ring (pre-allocated completion pool)

Expected gain: **-40% latency p99, -30% stack usage** per request.

### 3.1 Fixed buffer ring instead of stack arrays

**Problem:** Per-request stack arrays (`read_buf[4096]`, `write_buf[4096]`, `head_buf[8192]`) waste stack space and force re-initialization on every new conn. TigerBeetle pre-allocates a fixed pool of buffer structs.

**What to change:**
- New file: `lib/zigora_core/buffer_pool.zig` — fixed-size ring of `struct PerRequestBuffers { read: [4096]u8, write: [4096]u8, header: [4096]u8 }`.
- `Service` gets a `buffer_pool: BufferPool` field initialized in `init()`.
- `startService` allocates/returns buffers from the pool inside the accept loop.
- `processNew` borrows returned buffers vs stack inside function bodies.

**Files:** New `lib/zigora_core/buffer_pool.zig`, `lib/zigora_core/service.zig`, `lib/zigora_proxy/root.zig`.

**Commits:** `feat(core): ring buffer pool` + `feat(core,proxy): wire buffer pool into request path` 2 commits.

**Lines:** ~80 lines total (pool struct + borrow/return + wiring).

**Gain:** 20KB less stack per request. Few L1 cache evictions between requests. No .text section growth (reuse not reallocate). Tangent: connection re-use pool works with pool — a recycled stream gets a recycled buffer pair.

## Phase 4 — Parallel accept (multi-listener)

Expected gain: **+3x throughput** on multicore.

### 4.1 Accept on N sockets simultaneously

**Problem**: `startService` has one listener → one `accept()` per iteration. On a 4+ core machine, this means core 0 handles all accepts while cores 1-3 idle.

**What to change:**
- `Listeners.build()` already returns an indexed array of listeners.
- Change accept loop from:
  ```zig
  var listener = built[0];
  // accept loop on one listener
  ```
  To:
  ```zig
  // spawn N accept futures, one per listener, each with shared inflight group
  for (built, 0..) |l, i| {
      futures[i] = io.async(acceptLoop, .{ l, i, self, io, self.shutdown_watch });
  }
  ```
- Parallelized accept loop shared across cores.

**Files:** `lib/zigora_core/service.zig` + `lib/zigora_core/listeners.zig` (may reuse `SO_REUSEPORT` for multiple acceptors on the same socket).

**Lines:** ~30 lines.

**Gain:** The proxy is single-threaded accept constrained. 4 listeners → 4x throughput (linear up to # of upstream connections, then client-bound).

## 5 — Tiger style io_uring (only after phases 1-4)

Expected gain: **+5-10%** on already-optimized paths.

### 5.1 Hand‑rolled `io_uring` submission loop

**Problem:** `std.Io` goes through the Zig standard library's `Dispatch` layer — itself using `io_uring` on Linux, but with a generic worker pool design. Hand-rolling eliminates one extra dispatch pointer + reduces cache misses on the hot SQEP path.

**What to change:** Replace the `Server.runForever` spawn loop with a direct `io_uring` loop that manages:
- SQ submission (OP_ACCEPT, OP_CONNECT, OP_READ, OP_WRITE)
- CQ completion (user_data identifies the completion handler)
- No std.Io.Dispatch indirection

This is roughly 300-600 lines of lock-free ring code + 200 lines of handler/state machine per operation type (accept, connect, io, close).

**Files:** New `lib/zigora_core/ring.zig` (hand-rolled uring loop).

**Gain:** Could get ~80% of max_raw throughput, but given that `std.Io` already is `io_uring` underneath, the marginal gain over correct batching is ~5-10% — worth pursuing only when all other bottlenecks are resolved.

## 5 — Branch/Hint optimization

### 5.1 @branchUnpredictable on histogram keys

**Problem:** Ketama hash lookup (CRC32) results are inherently random — the downstream router selector returns a random resolver. This is a prime candidate for `@branchUnpredictable`.

**Where**: `lib/zigora_lb/root.zig` — the `Consistent.next` `for` loop (linear lookup by address) runs on every request but the target index is unpredictable.
```zig
// Before
for (self.backends, 0..) |b, i| {
    if (std.Io.net.IpAddress.eql(&b.addr, target)) return i;
}
// After
for (self.backends, 0..) |b, i| {
    if (@branchUnpredictable(std.Io.net.IpAddress.eql(&b.addr, target))) return i;
}
```

**Lines:** 1 line changed per selection loop.

**Expected:** ~5% latency reduction on consistent hashing selection.
